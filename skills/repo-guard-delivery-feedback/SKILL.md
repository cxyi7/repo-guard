# Repo Guard 交付反馈

## 先选择配置入口

存在 `repo-guard.delivery.json` 时先校验当前 `version: 2` 绑定并使用独立模式；关闭时保留资料，不自动切换入口。否则按 `repository.deliveryContract` 使用仓库内合同包。两种入口不能同时启用，不混用 JSON findings 与 Markdown FND 证据格式。

## 独立共同合同模式

1. 将真实问题关联到共同合同里的需求、责任参与方和问题提交，区分实现缺陷与需求、设计变化。共同合同没有约定的检查先经过定义修订和人工确认，不能事后编造失败证据。
2. 实现缺陷使用声明了 `testFiles` 的回归检查，在问题代码提交上实际执行 `delivery run --participant <id> --check <id>`，保留签名失败记录。测试应覆盖该缺陷；不要把工具缺失或环境错误冒充代码回归失败。
3. 用 `delivery feedback --participant <id> --id <问题标识> --requirement <需求标识> --description <问题说明> --check <回归检查> --improvement <改进说明> --improvement-check <改进检查>` 登记。命令引用真实失败记录，提高合同修订并清除旧确认。
4. 在权威合同来源评审修改，向人工展示责任划分、失败证据和反向改进义务；同步各仓固定副本并重新绑定。由人工负责人重新批准，AI 不读取或使用 reviewer 私钥，不冒充确认。
5. 修复代码后在新的干净提交上运行同一回归检查。检查定义与 `testFiles` 的内容必须和失败证据一致，不能通过改弱测试形成绿色结果；同时完成声明的改进检查。
6. 重新收集各方证据，针对当前版本组合执行联合验证，再交人工实际复测和验收。需求或设计本身变化直接修订合同约定，不伪造实现缺陷的红绿记录。

改进可以是永久回归测试或合适的团队检查，不要求把每个问题升级成全局规则。保留历史失败证据和修订，不删除反馈来消除待办。

## 仓库内合同包模式

每个正式问题使用一个独立 `findings/FND-*.md` 文件，避免主合同和单一发现文件持续膨胀。开始前阅读 [references/feedback-workflow.md](references/feedback-workflow.md)。

## 工作流

1. 判断问题是否达到正式 FND 条件；普通中间失败只保存在执行日志。
2. 从 [assets/finding.md](assets/finding.md) 创建独立发现文件，先把 `<REQUIRED_FINDING_ID>` 替换为本合同中全局唯一的 `FND-*`，再记录发现者、阶段、问题提交、关联任务和重复特征。资产中的 `pending` 故意不能通过最终 Gate。
3. 未进入终态时重新打开关联任务。
4. 实现缺陷保存同一回归测试在问题提交失败、最终代码提交通过的红—绿证据。
5. 测试环境或人工验收反馈按参考中的变体记录实际部署提交和 `HUMAN-RETEST-*` 人工复测；拒绝或延期按另一变体记录调查、关闭原因和人工确认。
6. 分别分析测试、合同、设计、任务模板和 Gate 是否升级，并等待人工确认升级决定。
7. 已关闭合同的问题建立新的 `repair` 合同，不篡改原合同完成历史。

## 边界

- 不把每个问题都升级成全局 Gate。
- 不删除或覆盖进入 Git 历史的 FND。
- 不代替人工确认拒绝、延期、升级结论或复测结果。

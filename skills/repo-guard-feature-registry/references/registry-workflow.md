# 功能归属判断

## 登记表根结构

登记表根对象固定使用 `schemaVersion: 1` 和 `features` 数组。登记表不存在时，从空根结构开始，不自行添加额外根字段：

```json
{
  "schemaVersion": 1,
  "features": []
}
```

每个节点的 `id` 必须是跨整棵树稳定且唯一的机器标识；移动节点、修改名称或继续完善同一业务能力时不更换 `id`。本地需求和 UI 来源只有已经保存且受 Git 跟踪时才填写仓库相对路径，否则保持 `null`。只有人工明确确认归属后，才能把 `status` 从 `proposed` 改为 `active` 并填写真实的 `confirmedAt`、`confirmedBy`。

## 判断顺序

1. 比较业务目标是否相同，而不是只比较页面、文件或接口名称。
2. 比较被验收和被回滚的边界是否相同。
3. 检查现有树中是否已有稳定功能身份。
4. 检查同一功能的活动合同、关闭合同和历史 `FND-*`。

## 合同关系

- 同一业务能力的继续完善通常沿用 `featureId`，但形成新的独立交付时新建合同。
- 活动合同定义发生变化时提升 `contractRevision` 并重新人工确认。
- 已关闭合同发现实现问题时新建 `repair` 合同，通过 `relations.repairs` 关联原合同。
- 新需求具有独立验收、发布或回滚边界时，建立子功能或同级功能，不挤入既有节点。

## 人工确认输出

在修改登记表前向人工展示：候选路径、选择理由、备选归属、合同关系和仍未解决的问题。

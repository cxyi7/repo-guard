# 多文件合同工作流

## 文件职责

- `DC-*.md`：唯一主合同和分支选择入口。
- `requirements/rev-NNN/requirements.md`：当前需求来源、事实、确认和整批指纹。
- `traceability.md`：每条需求事实到设计、任务、资料和验证的映射。
- `obligations.md`：受约束的 GFM 执行清单。
- `findings/FND-*.md`：每个正式交付发现一个文件。
- `spec.md`、`design.md` 等：仅在资料计划选择 `file` 时创建。
- `evidence/runs/RUN-*.md`：一次可复核的最终证据批次。

资产目录中的文件是可填写的结构脚手架，不是可直接通过 Gate 的完整示例。`<REQUIRED_*>` 表示必须由当前仓库事实替换的标识或路径，`pending` 表示尚未产生或尚未确认的提交、时间、指纹、模式或结论。不要把占位值改成看似合法的零哈希或虚构日期。

复制完成后必须保持三组关系一致：主合同 `materials` 指向组成文件，所有组成文件使用同一 `contractId`，功能登记节点的 `deliveryContracts` 使用主合同 ID 和仓库相对路径。需求事实 `REQ-*` 必须由 `traceability.md` 映射到 `obligations.md` 中真实存在的 `TASK-*` 与 `TEST-*`。

## 定义与执行状态

需求、资料计划、正文定义、追踪关系、义务定义和 Git 边界属于合同定义。勾选状态、证据引用、人工验收和 FND 处理进度属于执行状态。不要因为只更新执行状态而提升合同修订。

## 人工暂停点

功能归属、合同定义、范围扩大、并行协调冲突和最终验收都必须等待人工明确确认。

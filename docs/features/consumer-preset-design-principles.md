# 消费项目预设设计原则

本原则针对 repo-guard 为**将来接入的消费项目**提供最佳配置、默认预设和接入建议。应假设消费项目尚未建立任何代码规范；不是把 repo-guard 自身当作没有规范的项目。本仓库仍遵守现有开发、测试、文档和发布约束。

## 先建立规则，再验证代码

- 不得以“代码已经遵守所建议的规范”为检查有效的前提。不能假设公共方法已经位于 `utils`、类型定义已经位于 `types`、图标已经使用指定名称，或者业务层已经按推荐目录划分。
- 可以提出新的命名、目录、依赖方向和使用规则，但必须说明接入过程：盘点实际代码，确认目标规则和检查范围，报告存量差异，再按团队决定整改。
- 能直接解析的事实按语法或结构检测，例如文件扩展名、声明、导入关系、模板指令和属性值。业务角色不能仅凭文件名、类名或目录名推断；需要项目明确登记时，应说明前置条件。
- 默认路径只是初始配置建议，不是项目已经采用该结构的证据。用户可以修改预设，执行器以已确认的配置为准；不为迎合预设偷偷改路径、关闭失败规则或排除存量问题。
- 没有匹配目标不等于符合规范。接入验证必须核对实际代码与配置范围，展示已覆盖、未覆盖和无法判断的部分；增量检查没有变更与首次全量检查没有匹配是不同情况。
- “配置范围内通过”不能表述成“整个项目合规”。解析不了应报告无法验证，不能当作没有问题；静态检查也不能被描述成证明浏览器或业务运行结果正确。
- 最佳配置必须说明：要建立什么规则、从哪些事实检测、需要填写哪些项目参数、存量代码如何处理，以及已知边界。
- 验证样例应包含任意目录和命名、违反规范的源码、空匹配、无法解析及尝试绕过的情况，不能仅使用已经符合预设结构的示例。

## 在 Token 检查中的应用

Token 使用检查根据样式声明和属性值识别，不依据组件是不是叫“图标”或类名是否带指定后缀。指定值以明确登记的清单、来源、语言和位置为准；这些登记是准备建立的规则，不是通过观察现有错误值自动批准它们。

当前执行器检查配置选中的文件，并额外检查 `values.definitions` 指定的来源。它不能自动证明扫描范围覆盖消费项目的全部样式。接入时必须盘点实际目录、语言、生成方式和排除项，再配置 `include`、`exclude`、`languages` 与输出映射；源码检查通过不覆盖未选文件、JS 动态样式或浏览器行为。

后续 Skill 负责分析并提出配置，npm 包负责确定地执行已确认的规则。尚未实现自动接入或覆盖范围核对的部分，应记录在[Skill 接入待办](skill-integration-backlog.md)，不能提前承诺已有能力。

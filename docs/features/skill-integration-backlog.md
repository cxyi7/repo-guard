# Skill 接入待办清单

所有接入建议遵守[消费项目预设设计原则](consumer-preset-design-principles.md)。先盘点实际源码位置、语言和角色，再提出规范及配置，不能假设待接入项目已经使用 `src`、`utils` 或规定的组件名称。接入验证须展示实际覆盖范围，空匹配、未选语言和未覆盖目录不得默认为项目合规；这一自动核对流程尚待后续 Skill 实现。

[功能索引](README.md) · [前端工具预设](frontend-tool-presets.md) · [前端性能预设](frontend-performance-presets.md)

本文件只记录后续需要 Skill 完成的接入工作，当前不新增或分发自动接入 Skill。工程预设、依赖要求查询、配置校验和执行能力继续保留；项目特有的依赖、路径、脚本及页面目前需要接入者配置。

以下条目是能力待办，不代表每项必须单独建立一个 Skill。后续可以逐项实现，再决定合并为一个接入 Skill 或拆分。已有交付合同相关 Skills 保持原状。

## 统一边界

- Skill 负责读取项目、选择兼容工具、安装缺失依赖、补齐配置和实际验证；npm 包按保存的配置执行，不在日常检查中重新猜测项目身份或路径。
- 默认规则与可配置选项以包内预设、Schema 和能力要求为准，避免在 Skill 中复制另一套版本或规则表。
- 默认配置写入 `repo-guard.config.json`。已有用户值优先，原生工具配置按各适配器支持的语义合并；对象补缺、数组整项替换，不能简单拼接。JS 配置函数、插件实例等不能当作普通 JSON 合并。
- 用户可以手动调整配置；AI 不得为了通过检查降低阈值、扩大排除项、删除测试或关闭失败检查。
- 重复接入不重复追加脚本或插件；关闭功能不自动卸载依赖、删除配置。
- 默认开启不等于已经可运行。缺少工具、真实目录、路由或环境时，应记录待补齐项，不能用空脚本、虚构页面、旧报告冒充成功。

## S01：项目身份、多应用与工具链分析

**读取什么：** 仓库指令、工作区状态、应用清单、package.json、锁文件、Node 版本、包管理器、源码目录、Vue/TypeScript/Vite 配置及现有 scripts。

**需要做什么：** 区分应用根目录与仓库根目录；复用已确认身份。首次接入结合用户描述与项目事实提出身份建议，不确定时由用户确认。识别已有构建器，不把所有前端都当作 Vue + Vite。

**补充什么：** 明确的 project.id/role/stack/preset、多应用配置位置、每个应用的执行目录及工具链事实清单。使用 `createProjectDocument` 和 `normalizeProjectDocument` 等现有接口生成、校验配置，不自行发明字段。

**如何验收：** 每项检查落到正确应用；后续执行无需重新识别身份，不会修改其他应用。无法支持的技术栈明确记录适配缺口。

## S02：依赖选择、安装及兼容验证

**读取什么：** 启用的检查、`getFrontendToolRequirements(config)`、已有依赖及锁定版本、原生配置引用的插件、候选版本 engines/peerDependencies。

**需要做什么：** 复用已安装且兼容的工具，只安装缺失依赖；使用项目原包管理器和锁文件，选择经过兼容核对的精确 devDependency。不能直接安装 latest，也不能用强制忽略依赖冲突代替兼容验证。

**补充什么：** 每项能力对应的依赖、精确版本、选择依据；同步 package.json 与原锁文件。工具要求查询并不穷举任意原生配置中的全部依赖，仍需读取该配置补齐插件。

**如何验收：** 从消费项目自身解析并运行工具；Doctor 与真实命令均能执行。安装成功但检查发现代码违规时，分别报告接入状态与代码问题。

## S03：ESLint 接入

**读取什么：** JS/TS/Vue 使用情况、ESLint 版本、原生配置形式、插件、忽略规则、TypeScript 项目引用和源码范围。

**需要做什么：** 配置 ESLint、Vue、TypeScript 及类型感知规则所需依赖与解析环境；处理配置形式和工具版本兼容。保留用户原生规则，避免与格式化规则冲突。

**补充什么：** `checks.eslint` 的项目适配项、所需插件及类型项目范围。规则默认值取自程序预设，不在 Skill 中重写一份。已有 eslint.config.mjs 等文件不被覆盖。

**如何验收：** 对实际 JS/TS/Vue 文件执行检查，确认类型感知规则确实生效；通过现有生效配置查询确认用户覆盖优先。Hook 仍只处理暂存文件。

## S04：Prettier 接入

**读取什么：** 原生 Prettier 配置、忽略文件、已安装插件与项目文件类型。

**需要做什么：** 安装兼容 Prettier 及真正需要的语言插件；处理检查范围、忽略项和其他格式化工具的冲突。

**补充什么：** `checks.prettier` 的项目配置及必要依赖。保留 .prettierrc.json 等原生设置，不重复生成相互冲突的配置文件。

**如何验收：** 在真实文件上确认生效选项与用户覆盖一致；接入时不顺带进行未经授权的整仓格式改写。

## S05：Stylelint 接入

**读取什么：** CSS/SCSS/Less、Vue style 块、现有 Stylelint 配置及 styles 目录。

**需要做什么：** 按实际样式语言选择语法解析器、规则包和属性排序插件，确保 Vue 单文件组件中的样式可被解析。

**补充什么：** `checks.stylelint` 的范围、overrides、customSyntax 与必要依赖，合并用户规则。类名 kebab-case、属性排序沿用已确认预设；不额外开启颜色字面量、全部 px 或 no-descending-specificity 限制。

**如何验收：** 每种实际存在的样式语言至少验证一个文件，检查排序及命名规则；不通过排除整个 styles 或 Vue 范围消除报错。

## S06：TypeScript 类型检查接入

**读取什么：** tsconfig 文件与 references、路径别名、Vue 版本、类型声明、生成类型及实际源码范围。

**需要做什么：** 根据明确技术栈选择 tsc 或 vue-tsc，核对 TypeScript 与相关工具版本；确认前端、构建配置和测试类型项目的边界。

**补充什么：** `checks.typeCheck.options` 的 tool、configFiles 与项目适配项，以及实际 typecheck 脚本。类型文件归位以 `src/types` 默认或用户修改后的目录为准。

**如何验收：** 完整类型检查能读取真实项目，用户原生 compilerOptions 优先；不会遗漏 Vue 模板类型，也不会把类型检查加入 pre-commit。

## S07：文件组织与维护规则适配

**读取什么：** 源码、测试、类型、样式、生成文件的真实目录，以及已有命名、文件头和函数文档约定。

**需要做什么：** 对照已确认预设检查适用范围。测试默认 src/tests、类型默认 src/types、样式默认 styles；用户改过目录时读取实际配置。迁移文件属于代码修改，须同步引用并验证，不能仅改检查路径。

**补充什么：** `checks.pathNaming`、`maxFileLines`、`filePlacement`、`functionDocs`、`fileHeader`、`asyncResourceCleanup` 的项目路径与适用范围；分类行数阈值仍沿用程序预设。

**如何验收：** 正常文件不会被错分，违规文件能给出明确位置；生成文件等例外有事实依据。保留用户明确关闭的 deadCode 或 repository.codePlacement；新前端预设的 deadCode 默认开启。

## S08：架构依赖与业务分层适配

**读取什么：** 实际模块目录、业务领域、公共层、接口层、状态层、页面/组件关系和路径别名。

**需要做什么：** 把团队已确定的分层关系映射为可执行依赖规则，配置 dependency-cruiser 的解析范围与别名。不能仅凭目录名称判断业务职责。

**补充什么：** `checks.architecture` 中具体边界、范围和有依据的例外。跨业务目录的引用是否合理无法自动确认时，记录需要负责人决策的关系。

**如何验收：** 实际依赖图可解析，禁止的反向依赖和循环能被识别。此前取消的依赖包 src/internal 路径限制不重新加入。

## S09：公共方法单元测试

**读取什么：** `checks.unitTest` 的源码范围与测试映射、实际公共方法职责、输入输出、调用方和已有测试。

**需要做什么：** 按正常值、零值、边界、精度、非法输入梳理场景，优先复用有效测试；确实不适用的场景记录理由。断言依据业务预期，不照抄实现结果。

**补充什么：** Vitest 配置、实际测试脚本、公共方法测试文件与映射。默认可从 src/utils 映射到 src/tests/utils，但必须以用户配置为准；文件重命名后同步引用与映射。

**如何验收：** 测试覆盖实际公共方法并能检出错误结果；本阶段不新增 Vue 组件交互、端到端或 axe 测试。

## S10：覆盖率与变异测试

**读取什么：** 已确定的公共方法范围、Vitest/Stryker 配置、覆盖率报告路径、现有工具版本与阈值。

**需要做什么：** 使单测、覆盖率、变异测试指向同一批实际公共方法；覆盖率插件与 Vitest 匹配，Stryker core/runner 版本匹配且兼容当前 Vitest。

**补充什么：** `checks.coverage`、`checks.mutationTest` 的项目路径、必要依赖、测试适配器与报告配置；复用用户原生配置。

**如何验收：** 生成本轮覆盖率和变异报告，识别未覆盖或未被测试杀死的变异。不得降低阈值或排除失败方法；超时、工具错误与测试质量不足分别报告。

## S11：生产构建与产物预算

**读取什么：** 实际构建命令、构建器、产物目录、manifest、base、生产环境变量及清理方式。

**需要做什么：** 将实际脚本和目录写入配置，使预算扫描的就是本轮产物。根据项目设置生产压缩、CSS 拆分和 source map，用户原生构建选项优先。

**补充什么：** `checks.build.script/options/artifactBudget` 中的项目适配项、必要的 manifest 和清理脚本。不能写死 dist，也不能用空脚本代替构建。当前 Vite 适配不能直接套到 webpack 等构建器。

**如何验收：** 实际构建、旧产物清理、清单完整性及预算都能检查；超预算保留原阈值并报告原因。普通构建不会自动部署。

## S12：包体积分析

**读取什么：** Vite/Rollup 配置、原有插件、原生 build 选项及报告目录。

**需要做什么：** 安装兼容 rollup-plugin-visualizer，在现有配置中接入 `@cxyi7/repo-guard/vite` 的 `createFrontendBuildPlugins`，保留异步配置函数、原有插件和用户手工分包策略。

**补充什么：** `checks.build.bundleAnalysis` 的实际报告路径和格式；插件 root/configFile 指向明确应用。报告与部署产物分离，重复接入不重复添加插件。

**如何验收：** 同次生产构建生成 HTML、JSON、模块清单和中文摘要；预览不清空报告；模块分析与实际产物预算分别解释，不能拿模块渲染大小冒充最终传输大小。

## S13：Lighthouse 页面与浏览器环境

**读取什么：** 实际业务路由、访问权限、稳定页面标识、生产预览命令、端口、测试数据、Chrome 和 Puppeteer 环境。

**需要做什么：** 选择真实存在的首页、列表、详情或重页面；配置对应 url、expectedUrl、selector，确认不是登录页或空壳页。启动服务本轮产物目录的生产预览，避免使用开发服务器或旧版本服务。

**补充什么：** `checks.lighthouse.pages` 与 `options.ci.collect.url`、startServerCommand、就绪条件、超时、Chrome 配置和必要依赖。需要登录时复用用户 puppeteerScript，并按会话方式配置存储保留；凭据从环境变量读取。

**如何验收：** 最终有效 URL 与 pages 逐项一致，真实页面身份验证通过，每页产生配置次数的本轮报告，并执行性能断言。当前精确 URL 验证不适配 staticDistDir 自动改端口，应使用明确预览命令。采集失败或跳转错误不能以调低评分阈值解决。

**保留约束：** 原生 lighthouserc 配置优先；默认三次、中位数、桌面性能，不恢复已删除的测试类别；prePush 按独立开关选择，禁止进入 pre-commit，不隐式上传报告。

## S14：配置同步、幂等执行和失败恢复

**读取什么：** 接入前文件内容、Git 暂存/未暂存修改、现有 Hook、scripts、AI 规范和锁文件。

**需要做什么：** 在修改前保存本次涉及文件的原始内容及摘要。通过受支持的 init/enable 等入口同步配置、Hook、scripts 和托管 AI 规范；遇到未知托管标记按程序报错处理。

**补充什么：** 本次变更清单、合并结果、备份与恢复记录。重复执行应保持稳定，不额外追加 imports、plugins、scripts 或忽略规则。

**如何验收：** 安装或配置失败时，只恢复本次修改且未被并发更改的内容，保留原有工作；恢复锁文件后按原锁重新安装。不能使用整仓 reset/clean 回滚用户工作。工具接入成功但发现代码违规时，保留正确配置并记录问题。

## S15：接入验收与交付流程衔接

**读取什么：** 各项接入记录、最终配置、实际命令结果、本轮报告以及项目已启用的交付合同。

**需要做什么：** 先做配置校验与 Doctor，再运行真实检查。区分接入缺项、执行错误、规则违规和通过，不能把“依赖已安装”当作“所有检查通过”。

**补充什么：** 实际依赖版本、用户覆盖项、路径/路由、执行命令、报告位置、失败原因和需人工决定的事项。开启合同的项目沿用已有合同、证据及负责人验收流程。

**如何验收：** 可以从实际记录复现检查结果；人工验收由负责人完成。接入不自动授权 CI 部署、生产发布或代签合同。

## S16：图片资源、动态接口与页面图片接入

**读取什么：** 图片目录、根 styles、别名、公开目录、部署前缀、API 调用及响应字段、图片组件的实际 DOM、Sharp/SVGO/Lighthouse 版本。

**需要做什么：** 安装兼容 Sharp/SVGO，验证 keepIccProfile 等实际 API；按配置范围给出用途预算，补齐动态资源的 sourcePatterns、assetPatterns、reason，以及 api.method/endpoint/responseField。不根据未知接口取值推断所有图片已使用。

**补充什么：** imageAssets.governance、unusedImageAssets 的引用范围和接口说明、lighthouse.imageUsage 的路由预算、审计名称和自定义 DOM 映射；保留用户配置，数组整体覆盖。

**如何验收：** 全量命名/格式/预算检查，真实图片压缩候选，接口声明保留报告，浏览器图片观察及本轮 Lighthouse 报告。缺失审计明确未验证。显式批量更新先预览，检查无损像素、有损画质、动态路径和回滚结果；不自动删除原图或扩大全局忽略。这里只登记 Skill 工作，不提供 Skill 实现。

## T01：实现 AI 自动接入 Skill

当前不提供自动接入 Skill，已有交付合同相关 Skills 不等于工程自动接入已完成。

实施内容：

- [ ] 读取项目身份、目录职责、源码、依赖、锁文件、脚本与原生工具配置，形成明确接入计划。
- [ ] 补齐并复用包内可机器读取的能力要求；核对运行时、工具与插件兼容性，不在 Skill 中复制另一套规则或版本表。
- [ ] 使用项目原有 npm、pnpm 或 Yarn，复用兼容工具，为缺失依赖选择准确版本并安装。
- [ ] Java 按项目准备 JDK、Maven、检查工具、插件、规则文件与报告配置；不能按安装 npm 包的方式替代 Java 接入。
- [ ] 补齐 repo-guard 配置、目录绑定、执行脚本，以及需要同步的 tsconfig、POM、Vitest、Knip、Stryker 等原生设置。
- [ ] 保留用户配置优先级；重复接入不重复追加，关闭功能不自动删除依赖或配置，失败能恢复本次变更。
- [ ] 执行 Doctor 与真实检查，分别报告接入缺项、执行错误和代码违规。

验收标准：缺依赖的真实项目可完成安装与配置；已有配置及未提交工作不被覆盖；重复执行保持稳定；模拟安装或配置失败后能恢复；不通过降低阈值、扩大排除、删除测试或关闭检查来完成接入。

详细拆分见 [Skill 接入待办清单](features/skill-integration-backlog.md)。

## T02：完成真实消费项目验收

已有仓库回归、真实 Vitest 联调和历史 Java 原生工具验证。它们不能代替当前版本对所有接入组合的现场验收；新增目录配置后的真实 Maven 联动仍需补测。

实施内容：

- [ ] 分别准备 Vue、Node 和 Java Maven 消费项目，验证初始化、工具接入、执行、报告及修复后复查。
- [ ] 覆盖 JavaScript/TypeScript、已有原生配置、自定义源码与测试目录、单应用和多应用场景。
- [ ] 验证 npm、pnpm、Yarn 对应的安装和执行路径；记录实际测试的版本与环境，不能把未测组合算作通过。
- [ ] 在 Java 中真实验证目录改名后的 Maven 编译、JUnit 测试、覆盖率及相关报告范围；覆盖实际需要的多模块场景。
- [ ] 使用正常、违规、缺失文件、空匹配和工具执行失败样例，检查是否存在误报、漏检或假通过。

验收标准：每个已验证组合记录代码版本、环境、配置、命令、结果及日志；错误样例被检出，修复后通过；跳过和未验证项单独列出。不能用 Vitest 结果证明 Java 测试完成。

参考 [目录职责与路径绑定](features/directory-roles.md)、[Java 验收清单](java-check-acceptance.md)。

## T03：补齐合同中的生产前接口验收

当前已有交付合同和 Axios/k6 执行基础，尚未实现“合同开启时默认启用接口验收”的完整流程。

实施内容：

- [ ] 将接口验收纳入交付合同，合同开启时默认启用；明确应用、接口清单与覆盖范围。
- [ ] 合同声明参数来源、认证方式、测试数据、成功断言、必要场景及执行后的清理要求。
- [ ] Skill 根据项目和已确认业务约定生成测试，例如明确约定 `code === 1` 时按此断言；不能仅凭 HTTP 请求成功判定业务成功。
- [ ] 在候选版本部署到测试或预发布环境后、生产放行前执行，并记录实际目标版本。
- [ ] 核对清单与执行证据，识别未执行、跳过、失败及过期证据，阻断不满足合同的生产放行。

验收标准：缺少必需接口结果、参数缺失、业务断言失败或版本不一致时不能放行；正常执行可形成可追溯证据。接口成功验收不自动等同于负载或容量验收，不默认对生产执行写入性测试。

参考 [交付合同后续计划](features/delivery-contract.md#后续计划接口验收与受控挑拣未实现)。

## T04：补齐合同中的受控 cherry-pick

目前提交规范禁止 merge commit，但不能据此证明普通提交使用了 cherry-pick，也未实施受控挑拣流程。

实施内容：

- [ ] 在合同中记录源仓库、源提交清单、目标分支及目标版本。
- [ ] 记录源提交与目标提交的来源映射、挑拣范围及相关依赖。
- [ ] 记录冲突处理、额外修改和需要负责人确认的范围变化。
- [ ] 对挑拣后的实际目标版本重新执行工程检查与合同要求的验证，不能沿用源分支通过结果。
- [ ] 明确来源证据的可信边界，不把提交信息中的文字当作挑拣过程已被证明。

验收标准：缺少来源、遗漏必需提交、范围未经确认或挑拣后未重新验证时，不能完成对应交付；成功记录能够追溯本次目标版本及其验证证据。

参考 [交付合同](features/delivery-contract.md)、[提交信息规范](features/commit-message.md)。

## T05：修复普通 CI 的代码版本绑定

2026-09-14：已为普通 CI 和 delivery-check 接入版本一致性检查。当前 HEAD、索引、跟踪文件和所加载的仓库/应用配置必须与目标提交一致；检查前后、有效步骤之间及交付证据记录前复核。不修改或丢弃用户工作。

实施内容：

- [x] 保留目标提交超过行数限制、工作树或索引包含未提交修复的反例，必须阻断。
- [x] HEAD 不符、未提交变更、未跟踪源码、隐藏索引标记和未跟踪配置均阻断；子模块当前明确拒绝。
- [x] 验证检查脚本切换提交、多应用隔离、公共必检和交付证据记录边界。
- [x] CI 报告明确使用 base/head/phase，交付证据不能为不一致的执行对象签署通过结果。部署的实际产物绑定仍由 T06 跟进。

验收标准：未提交内容不能替目标提交通过检查；执行对象变化可检测并阻断；报告准确记录版本，失败分类复用公共结果与退出码。

实现：[版本检查](../src/orchestration/ci/subject.js)、[CI 执行](../src/orchestration/ci/runner.js)。验证：[反例测试](../test/ci/configured-ci.test.js)、[交付证据](../test/ci/delivery-receipts.test.js)、[多应用](../test/ci/workspace-ci.test.js)。忽略的依赖、外部服务和 Runner 本身不属于 Git 内容证明；无法防御检查脚本短暂修改后恢复内容的恶意行为。见 [CI 使用说明](features/ci.md)。

当前支持 GitLab 下 Node 应用独立运维，按质量、构建和部署顺序执行，生产需手动触发。Java 运维适配尚未实现；`ci` 与可选 `delivery-check` 不代表以下完整发布条件已实现。

实施内容：

- [ ] 增加 Java Maven 构建产物的部署适配，并明确目标运行环境。
- [ ] 开启合同的发布强制复核本次关联合同、必需证据与最终人工验收，不能仅凭普通质量检查通过放行。
- [ ] 绑定检查版本、验收版本、构建产物及部署版本，拒绝旧产物、旧证据和版本不一致。

- [ ] 增加部署后健康检查、结果记录、失败处理及回滚；涉及不可逆变更时明确实际可恢复边界。

验收标准：缺失合同验收、接口证据或版本不一致时不能部署生产；成功部署可追溯到实际产物与代码；故意制造部署或健康检查失败，验证阻断、结果记录及配置所承诺的回滚行为。

参考 [独立运维与按应用发布](features/operations.md)、[交付合同](features/delivery-contract.md)。
